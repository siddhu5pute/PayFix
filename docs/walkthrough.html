1. Start the project

First time on a laptop

  1. Install Git and Docker Desktop. Open Docker Desktop and wait for Engine running.
  2. Clone and enter the project: 
    git clone https://github.com/siddhu5pute/PayFix.git
cd PayFix
  3. Create the .env file (values are in the README's temporary section). In PowerShell: notepad .env → Yes → paste → save.
  4. Start everything (first build takes a few minutes): 
    docker compose --profile razorpay up --build -d
  5. Check all services are Up: docker compose --profile razorpay ps

Stop / reset

docker compose --profile razorpay down      # stop, keep data (site goes offline)
docker compose --profile razorpay down -v   # stop and wipe all payments + audit log
Only one laptop at a time may run the razorpay profile: the public address and the Razorpay webhook follow whichever laptop is running ngrok.

2. Two modes

Razorpay mode

With the .env file. The Pay button opens the real Razorpay Checkout (Test Mode, no real money). Webhooks come from Razorpay through ngrok. This is the default on our laptops.

Test payment: Netbanking → any bank → Success or Failure on Razorpay's test bank page.

MockPay mode

No .env file (rename it to .env.off), then docker compose down -v and docker compose up -d. Works fully offline.

The Pay button opens a test bank page where you pick the outcome. Extra scenarios: charged twice, authorized-only, flaky gateway.

Scenarios below are tagged both razorpay mockpay.

4. Scenarios: what to click

Before each scenario All flags off, DRY_RUN off, MIN_AGE 20 s, unless the scenario says otherwise. After a scenario, switch its flag back off.

S1 · Normal payment both

  1. Pay fee → Pay ₹1,000.00 securely.
  2. Razorpay: Netbanking → any bank → Success. MockPay: ✅ Pay successfully.
You'll see Status pending → paid within a few seconds, confetti. Control room → Webhooks: payment.captured and order.paid, "marked paid". PayFix steps stay grey: nothing to fix.
Say "Razorpay sends a signed webhook; the portal checks the signature before believing it. The browser's success callback is only a hint."
Underneath POST /pay → Razorpay order → Checkout → /payments/verify (signature checked, status NOT changed) → webhook with valid X-Razorpay-Signature → paid.

S2 · Lost confirmation: the main demo both

  1. Control room → turn DROP_WEBHOOKS on (red).
  2. Pay fee → Pay. Razorpay: Netbanking → Success. MockPay: 📶 Pay, then lose connection.
  3. Point at the status page: Portal says PENDING (MockPay: UNKNOWN) ≠ Gateway says CAPTURED.
  4. Wait 20–30 s with hands off (or Control room → ⚡ Run reconciliation now).
You'll see The 6 steps light up one by one, status flips to paid, confetti, blue "Fixed automatically by PayFix" banner, pop-up "PayFix just recovered ₹1,000". Control room → Webhooks shows them as "dropped by DROP_WEBHOOKS flag".
Say "The money left the bank but the confirmation was lost: exactly my incident. PayFix found it, asked Razorpay again right before acting, fixed it exactly once, and logged every step."
Underneath Engine loop: COLLECT (pending > 20 s) → DETECT (Razorpay says captured) → VERIFY (asks both again) → DECIDE (rule: captured ⇒ paid) → ACT (INSERT … ON CONFLICT DO NOTHING on UNIQUE(txn_id, action), then mark-paid on the portal's internal API) → LOG.

S3 · Payment fails both

  1. Pay. Razorpay: Netbanking → Failure. MockPay: ❌ Payment fails.
You'll see failed via the payment.failed webhook.
Say "A failure is final: nothing leaves failed, so a late or forged 'paid' can never flip it."
Variant Turn DROP_WEBHOOKS on first: the portal stays pending, and PayFix marks it failed (rule: gateway failed ⇒ failed).

S4 · Late webhook vs PayFix (race safety) both

  1. Control room → DELAY_WEBHOOK_SECONDS = 60.
  2. Pay successfully. Wait.
You'll see PayFix fixes it at ~20–30 s. When the late webhook finally arrives (60 s), the portal answers "already paid" and changes nothing.
Say "Two fixers, one payment: whoever comes second finds it already done. Every step is idempotent."
Try also DELAY = 5 s: the webhook wins, and PayFix's VERIFY step sees it's already paid and does nothing ("changed before act").

S5 · Duplicate webhooks both

  1. Control room → DUPLICATE_WEBHOOKS on. Pay successfully.
You'll see Status page → Portal status history: exactly one "→ paid". Logs: docker compose logs portal-backend | findstr DUPLICATE shows the second delivery ignored.
Say "Razorpay may deliver the same event twice. We store each event id once (UNIQUE), so the second copy is ignored."

S6 · Detect-only mode (DRY_RUN) both

  1. Control room → DRY_RUN on and DROP_WEBHOOKS on. Pay successfully. Run reconciliation now.
  2. Then turn DRY_RUN off and run again.
You'll see First: dashboard shows the mismatch and an ACT would_mark_paid entry tagged "dry run"; the payment stays pending. After DRY_RUN off: fixed.
Say "A safe way to switch PayFix on for a real portal: watch what it would do before letting it act."

S7 · Illegal status change both

  1. Control room → section 5 → on a paid payment click → pending (or → failed).
You'll see Red toast "Rejected by state machine: paid → pending". The status page history shows the attempt marked rejected.
Say "Nothing leaves paid or failed. Enforced in code and again by a database trigger, so even a raw SQL update is refused."

S8 · Abandoned payment both

  1. Pay → close the Checkout without paying.
  2. Wait ABANDON_AFTER_SECONDS (300 s in our .env).
You'll see PayFix marks it failed: "no payment ever reached the gateway".
Say "Stuck orders don't sit as pending forever, but PayFix waits long enough that a slow student isn't cut off."

S9 · Forged webhook both

In PowerShell:

curl.exe -X POST http://localhost:3000/webhooks/razorpay -H "Content-Type: application/json" -H "X-Razorpay-Signature: forged" -d "{}"
You'll see {"status":"rejected","reason":"invalid signature"} (HTTP 400). Control room → "Rejected (bad signature)" count goes up.
Say "Anyone can POST to a webhook URL. We check an HMAC of the raw body with a secret only Razorpay knows."

S10 · Charged twice mockpay

  1. DROP_WEBHOOKS on → Pay → 👯 Get charged twice.
You'll see Paid; dashboard "Duplicate refunds 1"; audit shows a REFUND step: first payment kept, second refunded.
Say "The second half of my incident: paying twice. Refunded automatically, exactly once."

S11 · Unclear gateway state mockpay

  1. Pay → ⏳ Authorized, not captured. Wait ~30 s.
You'll see Dashboard → Manual review queue gets the payment; status stays pending.
Say "When the gateway's answer isn't final, PayFix never guesses. A human decides."

S12 · Flaky gateway mockpay

  1. Control room → Fail next 3 → DROP on → pay (Pay, then lose connection) → Run reconciliation now.
You'll see Audit feed: RETRY gateway_transient_error entries, then the fix. With Fail next 8: manual review instead.
Say "Temporary errors are retried with exponential backoff; if they don't clear, a human takes over."

5. The 3-minute demo script

Incident story→S1 normal→DROP on→S2 lost confirmation→Dashboard replay→S7 illegal move
  1. 20 s: "Last semester my hotspot dropped mid-payment. The portal said Payment failed, wait 2–7 days. The bank had already taken ₹1,000."
  2. 30 s: S1. Show a normal payment turning paid.
  3. 60 s: Control room → DROP_WEBHOOKS on → S2. Point at Portal ≠ Gateway, wait for the steps, confetti and pop-up.
  4. 30 s: Dashboard → click the mismatch → timeline: "append-only, rebuilt from the log alone".
  5. 20 s: S7. Illegal move rejected.
  6. 10 s: "An independent referee: verifies before acting, acts once, keeps a permanent log."
Before presenting docker compose --profile razorpay down -v then up -d for a clean dashboard. Turn off laptop sleep. Open 3 tabs: Pay, Control room, Dashboard.

6. Questions you'll get

QuestionAnswer
Isn't the failure staged?The failure is simulated because a sandbox can't fail on command. The detection and the fix are real code against the real Razorpay API.
Why not just trust the webhook?Webhooks can be lost, late or duplicated. Reconciliation is the last line of defence.
What if two engines fix the same payment?UNIQUE(txn_id, action) + INSERT … ON CONFLICT DO NOTHING: one wins, the other logs SKIP. Tested with 5 racing workers and 100 payments × 4 workers.
Why wait 20 s (MIN_AGE)?So PayFix never races a webhook that is only slightly slow.
Why check Razorpay twice?The VERIFY step: state can change between detecting and acting. Never act on stale data.
Why two databases?An independent referee must not depend on the portal's internals, only its API.
How is the log tamper-proof?A Postgres trigger rejects UPDATE, DELETE and TRUNCATE on audit_log.
Why paise, not rupees?Floats can't represent money exactly (0.1 + 0.2 ≠ 0.3). Integers can.
Known limitations?Crash between claiming and acting isn't auto-recovered; Razorpay retries on the same order after a failure go to manual review; demo control room has no login; single machine.
